# 通用层硬编码检查（2026-10-27）

本轮在前一次 Profile 脚本归位后，复查六个仓库的运行代码、配置模板和工具入口。重点检查型号名称、现场设备身份、串口、地址、系统版本和个人目录是否被当作通用默认值。历史验证记录、测试样本和显式产品后端另行核对其实际用途。

## 发现并修正的问题

| 位置 | 原有问题 | 修改后行为 |
| --- | --- | --- |
| framework `config/deployment/release-spec.example.json` | 示例平台填入 aarch64 / Ubuntu 18.04 / glibc 2.27，容易被当作通用默认值 | 架构、系统发行版、libc、Python 和包来源改为目标环境占位值，必须由发行端填写 |
| plugins `protocols/mqtt/.../client.py`、`worker.py` | 客户端缺少配置时使用 `device_001/template_001`；worker 虽解析了 Core 身份，却未传给客户端 | 从 Core 身份继承设备 ID，显式配置冲突时拒绝；没有设备身份不能启用传输；不再推定模板 ID，空模板不能匹配任意注册响应 |
| plugins `motion/so101/.../calibrate.py` | 旧校准写入命令默认使用 `/SDCARD/URAN/config/uran_arm_calibration.yaml` | 写入命令必须指定 `--output`；probe 不需要输出文件。新 LeRobot 校准入口同样要求显式指定串口和输出路径 |
| plugins `tasks/autotask/.../mission_manager.py` | 录像默认选择 `cyberdog_main` | 请求录像的任务必须有 `media_actions.record_channel_id`，准备任务前检查；其他任务不受影响，录像请求失败不报告 recording_active |
| plugins 通用任务分发、导航安全提示 | 无后端或安全状态异常时，提示用户加载 CyberDog 工作区或检查 CyberDog 状态 | 保留原错误码和安全判定，提示改为检查所选导航/运动后端 |
| plugins `scripts/test.sh` | 优先选择 `/home/feiyu/miniconda3/bin/python3.13` | 使用 `URAN_PYTHON`，未指定时使用 PATH 中的 python3 |

同一轮将通用 managed-release 模板中的 CyberDog2 迁移说明改为适用于所有旧源码部署 Profile 的要求。具体产品迁移情况由产品说明记录。

## 保留项及边界

- `profiles/cyberdog2/` 是已有设备的旧产品装配。其现场身份、串口、厂商 namespace、系统环境以及 `legacy/scripts/` 只用于该 Profile，不进入通用脚本或空管理 bootstrap。这个旧装配仍需在产品切换时转换为新受控发行物；它不是可直接复用到另一台设备的通用模板。
- `motion/cyberdog2`、媒体的 CyberDog camera/WebRTC 后端，以及 autotask 的 CyberDog ROS2 后端属于明确选择的产品适配能力。厂商协议映射留在插件内部；未选择这些后端时不会导入/连接其厂商运行环境。这里没有把适配实现改名伪装成通用功能。
- 框架内关于旧 Linux/Python 的兼容注释、文档中的实机验证记录、单元测试中的设备样本是说明和覆盖范围，不参与生产型号选择。六仓库测试入口中列出 `motion/cyberdog2` 是对一个插件包执行测试，并不默认装载该机器人。
- bootstrap 包必须绑定构建时的架构、系统和 Python 版本，以防错误安装。这些信息从构建环境取得，属于确定发行物的平台约束，不是固定 CyberDog2 的运行分支。
- 本轮没有修改 CyberDog2 部署，也没有执行硬件命令。
