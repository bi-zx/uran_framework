# URAN 平台无关插件化软件架构说明

本文档描述 URAN 重构后的软件架构，重点说明系统分层、模块职责、插件机制、运行平台适配、通信关系和二次开发接口。文档不预先固化某一种机器人操作系统的通信名称、消息字段、服务形式、QoS 参数或配置格式，这些内容由平台适配和具体接口设计按业务语义确定。

URAN 的核心运行时、设备模型、领域服务和通用插件 API 采用平台无关的 C++ 接口。ROS 2 通过独立适配层接入，是当前优先实现的一种运行平台，不作为核心架构的固定依赖。未来接入其他机器人操作系统时，应替换或新增平台适配器，而不修改设备模型、领域语义和通用插件生命周期。

---

## 1. 总体架构

URAN 采用“平台无关核心 + 领域服务 + 业务插件 + 平台适配器 + 用户扩展”的结构。核心运行时提供稳定机制，领域服务组织业务能力，业务插件封装设备、协议和算法差异，平台适配器连接具体机器人操作系统。

```text
┌──────────────────────────────────────────────────────────┐
│                        用户扩展                          │
│   通用业务插件 / 平台专用模块 / 第三方算法与设备实现     │
└────────────────────────────┬─────────────────────────────┘
                             │ 领域 API / 平台服务 API
┌────────────────────────────▼─────────────────────────────┐
│                       领域服务层                         │
│       运控 / 媒体 / 传感器 / 任务 / 协议 / 存储         │
└────────────────────────────┬─────────────────────────────┘
                             │ Runtime 公共能力
┌────────────────────────────▼─────────────────────────────┐
│                 平台无关 URAN Runtime                   │
│ 插件管理 / 配置 / 状态 / 能力 / 语义路由 / 事件 / 诊断  │
└────────────────────────────┬─────────────────────────────┘
                             │ Platform Services
┌────────────────────────────▼─────────────────────────────┐
│                       平台适配层                         │
│       ROS 2 Adapter / 其他机器人系统 Adapter / Mock      │
└────────────────────────────┬─────────────────────────────┘
                             │
┌────────────────────────────▼─────────────────────────────┐
│              机器人操作系统、设备接口和基础设施          │
└──────────────────────────────────────────────────────────┘
```

各层职责如下：

- **Runtime** 只提供平台无关的运行机制，不包含设备型号判断、业务流程或具体机器人操作系统 API。
- **领域服务** 负责某一类能力的统一语义、协调逻辑和安全边界。
- **业务插件** 负责实现一个明确的业务变化点，例如设备适配、协议传输、格式转换或任务执行。
- **平台适配器** 把平台无关服务映射到 ROS 2 或其他机器人操作系统，不承载领域业务判断。
- **用户扩展** 通过领域 API、平台服务 API 或平台原生接口接入，不直接依赖 Runtime 内部类。

依赖方向保持从具体实现指向稳定抽象：

```text
具体设备、协议和用户实现       ROS 2 / 其他平台适配器
            ↓                           ↓
        领域插件 API                平台服务 API
            └────────────┬──────────────┘
                         ↓
                Runtime 公共 API
```

Runtime 不反向依赖任何具体业务插件或平台适配器，领域之间也不通过对方的内部对象进行耦合。

### 1.1 核心对象模型

系统运行时采用“设备—组件—插件实例—能力”的组织关系，并把插件实现单独作为代码层概念：

```text
Plugin Implementation（插件实现类）
             │ 可创建多个对象
             ▼
Device（设备）
└── Component（组件）
    └── Plugin Instance（插件实例）
        └── Capability（一个或多个能力）
```

这几个概念承担不同职责：

| 概念 | 含义 |
|---|---|
| Device | 对外作为一个整体管理和注册的设备，例如一台机器狗或一套移动操作机器人 |
| Component | 设备内部可独立描述、控制和诊断的逻辑组成，例如本体运动、机械臂、夹爪、前置相机和通信组件 |
| Plugin Implementation | 可被插件加载后端发现的 C++ 实现类，描述实现类型、类名和 API 兼容信息 |
| Plugin Instance | Runtime 根据装配配置创建的运行对象，具有独立的实例标识、所属设备、所属组件、配置和生命周期 |
| Capability | 插件实例或独立功能模块向系统提供的语义能力，例如移动、机械臂控制、拍照、定位或协议上行 |

插件实现与插件实例必须分开理解。一个串口协议实现类可以被创建为“本体串口”和“机械臂串口”两个实例；一个相机实现类也可以同时服务前置相机和后置相机。实现类不保存现场部署身份，设备标识、组件标识、实例标识、端口和地址等信息属于运行装配。

一个设备的典型组织方式如下：

```text
Device: robot_001
├── Component: locomotion
│   └── PluginInstance: dog_motion_main
│       ├── Capability: motion.velocity
│       └── Capability: motion.posture
├── Component: manipulator
│   ├── PluginInstance: arm_motion_main
│   │   ├── Capability: arm.joint_control
│   │   └── Capability: arm.pose_control
│   └── PluginInstance: gripper_main
│       └── Capability: gripper.control
├── Component: camera_front
│   └── PluginInstance: front_camera_main
│       ├── Capability: image.capture
│       └── Capability: video.stream
└── Component: communication
    ├── PluginInstance: mqtt_primary
    └── PluginInstance: websocket_backup
```

上层业务面向“哪个设备、哪个组件、需要什么能力”进行请求，领域服务和能力注册表再解析到实际提供者。插件类名只用于创建实现，不进入业务寻址关系。

### 1.2 两类扩展轴

URAN 同时存在两类相互独立的扩展：

```text
业务扩展轴                         运行平台扩展轴
运控 / 传感器 / 媒体 / 任务       ROS 2 Adapter
设备驱动 / MQTT / WebSocket       其他机器人系统 Adapter
算法和用户功能                    Mock / 本地运行 Adapter
```

业务插件实现“系统能做什么”，平台适配器实现“这些能力如何接入当前机器人操作系统”。更换 ROS 2、其他机器人操作系统或本地测试环境，不应改变 Device、Component、Plugin Instance 和 Capability 的关系。

ROS 2 不是 MQTT、WebSocket 一类的外部业务协议插件。外部协议属于协议领域，平台适配器则为 Runtime 和业务插件提供进程调度、通信、时间、日志、发现等基础运行能力，两者位于不同扩展轴。

### 1.3 平台替换关系

平台无关模块只能依赖 Platform Services 抽象，不能直接包含具体机器人操作系统的节点、消息、执行器或插件加载类型。平台适配器负责完成语义映射：

```text
URAN 平台服务语义
├── 持续数据发布与订阅
├── 请求与响应
├── 长时操作、反馈和取消
├── 时钟、定时和任务调度
├── 命名、发现和连接状态
└── 日志与平台诊断
          │
          ├── ROS 2 Adapter → Topic / Service / Action / Executor 等
          └── 其他 Adapter  → 对应平台的原生机制
```

平台抽象描述业务需要的最小语义，不复制某个平台的完整 API。若目标平台不支持某项服务，适配器应明确报告能力缺失，由装配或领域服务决定禁用、替代或降级。

默认部署可以只启用一个平台适配器，但架构不依赖“全局唯一机器人操作系统”这一假设。平台服务按接口和实例注册，可以支持迁移阶段多个适配器并存，由具体组件选择所需的平台服务。

## 2. 核心运行时

Runtime 是系统公共能力的承载层，其主要组件如下：

```text
UranRuntime
├── RuntimeAssembler         核心组件与领域服务装配
├── PluginManager            插件实例和生命周期管理
├── PluginLoader             插件加载后端抽象
├── ConfigManager            配置加载与配置快照
├── StateStore               统一状态空间
├── SemanticRouter           平台无关的语义路由
├── CapabilityRegistry       业务能力注册与查询
├── PlatformServiceRegistry  平台服务注册与选择
├── EventDispatcher          进程内事件通知
└── DiagnosticsManager       健康状态与诊断汇总
```

这些组件均面向平台无关接口工作。具体部署时可以合并在一个 Runtime 库中，也可以根据规模拆分；组件边界比包的数量更重要。

### 2.1 UranRuntime 与 RuntimeHost

`UranRuntime` 是平台无关的装配和运行入口，负责创建公共组件、连接领域依赖并驱动系统启动和停止。它是普通 C++ 对象，不继承任何机器人操作系统的节点基类，也不直接创建平台原生通信端点。

`RuntimeHost` 位于平台适配包中，负责把 UranRuntime 接入具体机器人操作系统。例如 ROS 2 适配包可以提供 `Ros2RuntimeHost`，由它持有 `rclcpp::Node`、Executor 和原生通信对象，再通过 Platform Services 与 UranRuntime 交互。更换平台时替换 Host 和 Adapter，UranRuntime 本身保持不变。

Runtime 和 Host 都不直接实现具体领域业务。Host 只做平台事件接入、数据模型转换和调度，业务判断仍由领域服务完成。

### 2.2 PluginManager

PluginManager 统一管理进程内 C++ 业务插件，主要承担：

- 发现并创建插件实例。
- 判断插件类型和接口兼容性。
- 向插件注入受控的运行上下文。
- 驱动配置、激活、停用和清理过程。
- 以运行实例为单位维护生命周期、能力和健康状态。
- 在加载或运行异常时隔离故障并反馈给所属领域。

PluginManager 只管理通用生命周期，不决定运动控制、任务切换等领域行为。涉及业务安全的插件切换由对应领域服务发起和裁决。

插件对象的发现和创建通过 `PluginLoader` 抽象完成。核心只依赖加载接口，不依赖某个机器人操作系统的插件框架。ROS 2 部署可以提供基于 `pluginlib` 的加载后端，通用部署可以采用动态库工厂，测试环境可以采用静态工厂或 Mock Loader。

### 2.3 PluginContext

PluginContext 是业务插件访问 Runtime 和平台服务的统一入口，用于替代插件对内部管理器及具体机器人操作系统对象的直接依赖。它可以向插件提供：

- 当前插件实例及其所属设备、组件的身份视图。
- 插件自身配置视图。
- 受权限控制的状态读写。
- 平台无关的日志、时钟、定时和任务调度接口。
- 持续数据、请求响应和长时操作等平台通信服务。
- 语义路由与平台服务查询。
- 事件、诊断和健康信息上报入口。
- 领域服务明确开放的其他能力。

Context 只暴露稳定接口，不暴露 PluginManager、StateStore、`rclcpp::Node` 或其他平台原生对象。这样 Runtime 内部实现和底层机器人操作系统都可以调整，而不影响平台无关插件。

确实需要直接使用某个平台原生 API 的实现，应明确标记为平台专用插件，并依赖对应适配包。它仍可由 Runtime 管理生命周期，但不宣称能够跨平台复用。

### 2.4 ConfigManager

ConfigManager 将系统配置、领域配置和插件私有配置组织为独立配置空间，并向使用者提供经过校验的配置快照。

配置架构需要能够表达配置来源、结构校验、版本、更新范围和失败恢复方式，但不在本架构文档中规定具体文件格式。插件只能访问分配给自己的配置，避免插件之间共享和修改无关配置。

### 2.5 StateStore

StateStore 提供统一运行状态视图，用于承载系统、设备、网络、控制、运动、媒体、任务、插件等状态。它解决的是状态所有权和跨模块访问问题，而不是替代所有业务数据通道。

状态模型需要能够描述字段所有者、数据类型、来源、时间信息、读写范围以及是否需要变化通知。核心字段由平台或领域服务维护，插件扩展状态按设备、组件和插件实例隔离。即使两个实例由同一个实现类创建，它们也拥有各自的状态和诊断空间；实例清理时，其受控状态视图负责移除该实例拥有的状态定义和值。

高频传感器流、图像流和大数据内容仍通过平台适配器提供的合适数据通道传输，不写入通用状态空间。

### 2.6 SemanticRouter

SemanticRouter 负责组织设备、组件、能力和消息类型之间的语义路由，使业务模块依赖“目标是谁、需要什么能力、执行什么操作”，而不是依赖某个平台的 Topic、Service、Action 或其他原生端点名称。

平台适配器维护语义路由与原生通信端点之间的映射。公共接口、领域接口和插件私有接口分别由对应接口设计确定，本架构不预先生成或固化所有平台端点。

### 2.7 CapabilityRegistry

CapabilityRegistry 记录当前系统实际可用的能力及其提供者。例如系统可以登记运动、拍照、定位、某类传感器、某类任务执行器或某种上行协议能力。

一个插件实例可以注册多个能力，同一种能力也可以存在多个提供者。能力记录关联设备、组件和实际提供者，必要时附带优先级、健康状态或选择策略。领域服务和插件在激活后登记能力，在停用或故障时撤销或降级能力；任务和用户扩展因此不需要识别具体设备型号或插件类名。

### 2.8 EventDispatcher 与 DiagnosticsManager

EventDispatcher 用于同一进程内的低耦合事件通知，例如插件状态变化、配置变化和连接状态变化。它不替代平台通信；需要跨进程、跨设备或供外部观察的事件通过当前平台适配器提供的通信服务发布。

DiagnosticsManager 汇总 Runtime、领域服务和插件的生命周期、外部依赖、错误和降级状态，形成统一的系统健康视图。具体诊断字段由后续接口设计确定。

### 2.9 PlatformServiceRegistry

PlatformServiceRegistry 记录当前可用的平台服务实现，例如通信、时钟、调度、日志、发现和平台诊断。业务插件按所需服务查询，不持有一个包含全部功能的全局“RobotOS 对象”。

同一类平台服务可以存在多个实例。例如迁移阶段可以同时注册 ROS 2 通信适配和另一套机器人系统的通信适配，由组件装配选择使用哪一个。平台服务的可用性也可以进入能力和诊断视图，使缺少某项平台能力时能够在启动阶段发现并降级。

## 3. 插件架构

插件用于封装系统中经常变化、需要替换或由第三方提供的实现。插件不等同于所有功能；稳定的领域协调逻辑仍保留在领域服务中。

### 3.1 插件类型

| 插件类型 | 主要职责 | 典型实现 |
|---|---|---|
| 协议插件 | 外部连接、收发、编解码适配和连接状态 | MQTT、WebSocket、专有协议 |
| 运控插件 | 统一运动语义与设备原生控制接口之间的适配 | 轮式底盘、机器狗、无人机适配 |
| 媒体插件 | 媒体源、转换、编码或传输的具体实现 | 相机源、编码器、RTSP/WebRTC 传输 |
| 传感器插件 | 原始数据接入、格式与坐标转换 | 气体、温湿度、雷达等适配 |
| 任务插件 | 可插拔的任务类型或任务执行器 | 巡检、拍照、路线执行、算法任务 |
| 存储插件 | 状态、事件或业务数据的持久化实现 | 本地文件、数据库、远程存储 |

插件类型可以扩展，但每类插件应由相应领域 API 定义能力，不使用一个包含所有业务方法的通用“大插件接口”。

### 3.2 接口组成

插件接口分为两部分：

1. **基础接口**：描述插件实现信息、接口版本、生命周期、能力和健康状态。
2. **领域接口**：描述插件在所属领域提供的操作，例如发送协议数据、执行运动命令、读取传感器或运行任务。

基础接口保证 PluginManager 能够统一管理插件，领域接口保证业务调用保持类型清晰。第三方插件只依赖公共 API 包，不依赖 Runtime 实现包。

### 3.3 插件实现与运行实例

插件实现描述代码本身，适合包含实现类型、实现版本、API 版本和导出类名等相对稳定的信息。运行实例描述一次实际部署，适合包含实例标识、所属设备、所属组件、平台路由作用域、启用状态和实例私有配置。

```text
LoopbackProtocolPlugin（一个实现类）
├── protocol_primary（实例，通信组件，主通道配置）
└── protocol_backup （实例，通信组件，备用通道配置）
```

PluginManager 以实例标识管理对象，而不是以实现类名管理对象。同一个实现类可以重复出现在装配配置中，每个实例分别完成配置、激活、停用和清理。实现类给出的静态描述用于兼容性检查，不应与运行实例标识绑定。

### 3.4 生命周期

插件生命周期采用统一状态模型：

```text
发现 → 创建 → 配置 → 激活 → 运行
                    │       │
                    └── 停用 ──→ 清理/卸载
```

- **创建**：建立插件对象，不连接外部设备。
- **配置**：读取配置，准备通信对象和内部资源。
- **激活**：连接设备或外部系统，开始提供能力。
- **停用**：停止输出、异步任务和外部交互。
- **清理**：释放线程、句柄、通信对象、实例状态和其他资源。

生命周期的具体函数形式由插件 API 定义。架构只要求 PluginManager 能够控制资源边界，并获得明确的成功、失败和健康结果。

### 3.5 发现与加载

Runtime 通过 `PluginLoader` 接口发现和创建 C++ 进程内插件，不直接依赖某一种平台的加载框架。加载后端负责把实现标识解析为对象工厂，PluginManager 仍统一负责实例身份、生命周期、能力和状态。

不同部署可以选择不同后端：通用环境可以使用动态库工厂，静态部署和测试可以使用静态工厂或 Mock Loader，ROS 2 部署可以使用基于 `pluginlib`/`class_loader` 的 Loader。加载后端的差异不应改变领域插件接口。

插件描述只关联实现类型、接口类型和 API 兼容信息，不承载设备标识或业务配置。插件选择、实例归属和实例参数由系统装配配置提供。Runtime 可以根据设备、组件和实例身份生成隔离的平台路由作用域；ROS 2 Adapter 可将该作用域映射为 ROS Namespace，其他平台则映射为各自的寻址机制。

### 3.6 故障隔离与运行形态

插件边界首先解决代码依赖和实现替换问题，并不天然提供进程级故障隔离。模块采用哪种运行形态，应根据稳定性和资源特征决定：

- 需要低延迟、直接调用和统一生命周期的实现，可作为进程内 C++ 插件。
- 资源消耗较大、可能阻塞、来源不受控或需要独立重启的实现，适合作为独立平台进程或平台原生模块；在 ROS 2 部署中可以表现为独立节点。
- 需要单独部署和升级的完整业务能力，适合作为独立功能包。

不同运行形态尽量使用同一套领域数据模型和通信语义，使进程内实现与独立模块可以替换。通用插件只依赖平台无关 API；确实需要直接调用某个平台原生能力的插件可以作为平台专用插件，但要在依赖和装配信息中明确标识，并限制在对应平台部署中使用。

## 4. 领域服务

领域服务位于 Runtime 与具体插件之间。它负责稳定的业务语义、能力编排和领域安全，避免这些逻辑散落到设备插件或协议插件中。

### 4.1 协议领域

协议领域由协议网关和协议插件组成：

```text
外部连接
    ↓
协议插件：连接、收发、重连、传输级编解码
    ↓
协议网关：统一业务消息封装、上下行选择、失败切换
    ↓
领域路由
```

协议插件不处理运动、任务、媒体等业务逻辑。外部协议发生变化时，只影响协议领域和必要的映射层，不影响其他业务模块。

同一设备可以同时装配多条协议通道，例如 MQTT 主通道、WebSocket 备用通道和本地调试通道。每条通道都是独立的协议插件实例，分别维护连接、配置、状态和诊断。ProtocolGateway 保存和选择的是协议实例，而不是协议实现类型；所谓主通道也只是当前策略优先选择的某个实例，并不限制设备只能注册一种协议。

协议选择可以根据设备、通道角色、消息类别、健康状态和业务策略逐步扩展。本架构只确定多实例和网关选择关系，不预先规定具体协议名称或固定路由表。

### 4.2 运控领域

```text
统一运动请求
      ↓
控制权、状态和安全检查
      ↓
运控服务
      ↓
运控插件
      ↓
设备原生控制接口
```

运控服务负责统一命令语义、控制权、限速、超时、急停和执行反馈；运控插件只负责统一命令与设备原生接口之间的转换。

任务模块和用户业务不直接调用设备运控插件，而是通过运控领域公开的能力发起请求。

### 4.3 媒体领域

媒体领域将媒体源、转换、编码、传输和会话管理分开：

```text
媒体源 → 格式转换 → 编码 → 传输
   └──────────── 媒体会话管理 ────────────┘
```

相机型号、编码方式和传输协议因此可以独立替换。媒体会话由领域服务统一管理，插件只实现其中一个明确环节或一组紧密相关的能力。

### 4.4 传感器领域

```text
设备原始数据
      ↓
数据源适配
      ↓
格式、单位和坐标转换
      ↓
标准领域数据
      ↓
平台通信接口 / 状态摘要 / 上层算法
```

传感器领域负责形成稳定的数据语义，具体设备消息和厂商 SDK 保留在插件内部。状态空间只保存需要共享的状态或摘要，不承载完整高频数据流。

### 4.5 任务领域

任务领域负责任务实例的创建、执行、反馈、暂停、恢复、取消和结果管理。任务插件实现具体任务类型，任务服务负责任务状态机和能力协调。

任务执行需要运动、媒体、定位或传感器能力时，通过对应领域服务申请，不持有具体插件对象。这样设备插件替换不会迫使任务实现同步修改。

## 5. 通信与数据流

### 5.1 下行流程

```text
云端或外部系统
      ↓
协议插件接收数据
      ↓
协议网关转换为领域消息
      ↓
消息路由识别目标领域
      ↓
领域服务进行校验、状态判断和业务处理
      ↓
领域插件或独立功能模块执行
      ↓
结果进入统一反馈链路
```

协议层只负责接入和转换，路由层只负责分发，领域服务负责业务判断，插件负责具体执行。

### 5.2 上行流程

```text
设备、插件或业务模块产生数据
      ↓
领域服务形成领域数据
      ↓
上行网关选择可用协议
      ↓
协议插件完成外部发送
      ↓
发送结果和连接状态进入诊断与状态视图
```

同一领域数据可以通过不同协议发送，业务模块不需要感知当前使用 MQTT、WebSocket 或其他传输方式。

### 5.3 设备注册与设备视图

设备对外注册不由某个 MQTT 或 WebSocket 插件单独拼装。Runtime 依据设备与组件装配关系，并结合能力注册表、协议网关、状态空间和诊断信息，形成当前设备视图：

```text
设备与组件装配
      +
已激活的插件实例与能力
      +
协议通道、状态和诊断
      ↓
设备注册快照 / 设备能力视图
      ↓
由选定的协议实例发送到外部系统
```

协议插件只负责传输这份设备视图，不决定设备包含哪些组件，也不自行声明其他插件的能力。这样切换外部协议不会改变设备模型，增加机械臂、相机或新能力时也不需要修改协议插件。

### 5.4 模块间交互方式

模块间根据边界选择交互方式：

- 同一进程、低开销且不需要对外暴露的调用，可使用 C++ 接口或内部事件。
- 跨进程、需要独立部署或需要被外部观察的交互，通过 Platform Transport 提供的通信语义完成。
- 持续数据、请求响应和长时间可取消操作使用与业务语义相符的平台服务，由平台适配器映射为原生通信机制。

例如，ROS 2 Adapter 可以将这些语义映射为 Topic、Service 和 Action，其他机器人操作系统则映射为其原生端点。架构不强制所有功能都插件化，也不强制所有内部交互都经过某个机器人操作系统；选择依据是模块边界、部署需求和故障隔离需求。

### 5.5 需要进一步约定的通信内容

公共接口和领域接口在落地时需要分别说明：

- 接口的业务语义、方向和所有者。
- 数据模型、单位、时间和坐标语义。
- 调用结果、异常和取消方式。
- 接口版本及兼容方式。
- 不同数据语义对可靠性、时效性和资源占用的要求。
- 多设备、多实例部署时的寻址、隔离和发现关系。
- 平台需要提供的能力，以及缺失能力时的拒绝或降级方式。
- 领域接口与平台原生端点之间的映射责任。

具体平台端点名称、消息定义和传输参数由对应平台适配及领域接口说明确定，本架构文档不提前固定。

核心与适配器之间使用平台无关的 C++ 数据模型。ROS 消息或其他平台原生消息只存在于适配层和平台专用模块中，由 Adapter 负责与领域数据模型相互转换，不能向内渗透到 Runtime、领域服务和通用插件 API。

## 6. 状态、配置和诊断关系

状态、配置和诊断是三个不同的视图：

- **配置** 表达系统期望如何运行，例如启用哪些插件以及插件参数。
- **状态** 表达系统当前处于什么状态，例如当前协议、控制模式和任务阶段。
- **诊断** 表达模块是否健康以及出现了什么问题，例如连接失败、插件降级或处理超时。

三者由 Runtime 统一提供访问机制，但内容所有权仍属于产生它们的组件。领域服务维护领域状态，插件维护自身运行状态，Runtime 负责汇总和对外提供统一视图。

设备级状态用于表达整机的汇总结果，组件级状态用于表达某个组成部分的业务状态，插件实例状态用于表达具体实现对象的运行情况。三者可以关联，但不互相覆盖。例如“机械臂不可用”可以由对应实例故障汇总而来，同时仍保留该实例自己的连接错误和诊断细节。

配置更新不直接修改状态；配置应用成功后，由实际执行组件更新运行状态。诊断也不代替业务结果，业务调用应通过本身的返回或反馈接口给出结果。

## 7. 二次开发接口

URAN 对外提供业务扩展和平台扩展两类入口。开发者可以只增加业务功能，也可以为新的机器人操作系统实现适配。

### 7.1 平台无关 C++ 领域插件

适用于设备驱动适配、协议实现、传感器转换、运动控制、媒体处理和任务执行器等需要嵌入领域服务的能力。

插件开发者只依赖公共插件 API、Platform Services API 和对应领域 API，不依赖 Runtime 实现或某个机器人操作系统。插件的实例化、配置、启停、状态和诊断由 Runtime 统一接管。

### 7.2 平台原生独立模块

适用于算法接入、数据处理、任务编排以及需要独立部署、升级或故障隔离的功能。开发者通过当前平台适配器公开的通信接口与 URAN 交互，不链接 Runtime 实现，也不访问进程内插件对象。

在 ROS 2 部署中，这类扩展可以是使用 `rclcpp` 的独立节点；在其他机器人操作系统中，则使用对应平台的原生模块形式。只要领域语义和平台通信契约保持兼容，独立模块可以单独编译、启动和升级。

### 7.3 平台适配器与平台专用插件

接入新的机器人操作系统时，实现 RuntimeHost、所需 Platform Services、数据模型转换和必要的 PluginLoader 后端。平台适配器只处理平台接入，不重新实现设备模型、领域服务或业务规则。

少数必须直接使用平台 SDK、原生消息或生态组件的功能，可以实现为平台专用插件。此类插件应与通用插件分包，显式声明所需平台能力，并且不能把平台类型加入公共 API。

### 7.4 可用扩展面

| 扩展面 | 用途 |
|---|---|
| 平台通信接口 | 接入独立模块、算法和外部业务功能 |
| 领域插件 API | 嵌入设备、协议、媒体、传感器或任务实现 |
| Platform Services API | 为通用插件提供通信、时钟、调度、日志等平台能力 |
| 平台适配接口 | 接入新的机器人操作系统或本地运行环境 |
| 能力注册接口 | 声明插件或独立模块可提供的能力 |
| 扩展状态接口 | 提供插件和用户功能的运行状态 |
| 配置入口 | 注入用户功能或插件自己的配置 |
| 事件与诊断入口 | 报告运行变化、健康状态和错误 |

这些扩展面共同构成用户接口。开发者不需要修改 Runtime，也不需要依赖其他具体插件。

### 7.5 扩展边界

用户扩展可以新增能力，但不能绕过领域服务直接修改其他模块状态、替换安全决策或持有 Runtime 内部管理器。涉及运动、控制权和设备安全的操作始终经过对应领域服务。

安全与访问边界按请求目标逐层表达：设备级操作面向整机，组件级操作只影响指定组成部分，能力级操作由对应领域服务校验后解析到实际提供者。这样机械臂插件不会因为与机器狗本体属于同一设备而自然获得本体控制权，协议插件也不会因为负责设备注册而拥有业务状态的写权限。

如果用户功能只消费或生产经平台通信接口公开的数据，优先作为当前平台的独立模块；只有确实需要嵌入领域执行链路、共享生命周期或降低调用开销时，才设计为进程内插件。若扩展需要平台原生 API，则应保持为平台专用模块或插件，不能因此扩大通用 API 的平台依赖。

## 8. 代码与部署组织

软件包按职责可归纳为四类逻辑模块：

```text
平台无关公共 API
├── 设备、组件、实例和能力模型
├── Runtime 与领域插件 API
├── Platform Services API
└── PluginLoader API

平台无关核心
├── UranRuntime 与 Runtime 装配
├── 插件、配置、状态和语义路由
├── 能力、事件和诊断
└── 协议、运控、媒体、传感器和任务领域服务

平台适配
├── ROS 2 Adapter、Loader 与 Bringup
├── 其他机器人操作系统 Adapter
└── Mock / 本地运行 Adapter

具体实现
├── 平台无关业务插件
├── 平台专用插件
└── 平台原生独立模块
```

实际工程可以根据维护团队和部署方式拆分软件包，不要求每个逻辑组件对应一个包。无论如何拆分，应保持以下依赖关系：

- 公共 API 不依赖 Runtime、平台 SDK 或具体实现。
- Runtime 和领域服务只依赖平台无关公共 API 与基础设施。
- 领域服务依赖 Runtime 公共能力和领域 API。
- 具体插件依赖相应 API，不反向成为核心依赖。
- `rclcpp`、`pluginlib`、ROS 消息和 `ament` 只存在于 ROS 2 Adapter、ROS 2 Loader、ROS 2 Bringup 和 ROS 2 专用插件中。
- 平台无关核心可以在没有 ROS 2 的环境中独立编译和测试。

部署时，可以将稳定且紧密协作的领域服务和插件组合在一个进程，也可以把媒体、第三方算法或高风险模块放到独立进程。部署形态变化不应改变领域语义和用户接口。

## 9. 与现有工程的对应关系

现有 `uran_ws` 中的功能可以按下表映射到新架构：

| 现有模块 | 重构后的主要归属 |
|---|---|
| `uran_core` | 拆分为平台无关 UranRuntime、领域服务和 ROS 2 RuntimeHost |
| `uran_move` | 运控领域服务和设备运控插件 |
| `uran_media` | 媒体领域服务及媒体源、编码、传输实现 |
| `uran_autotask` | 任务领域服务和具体任务执行器 |
| `uran_msgs` / `uran_srvs` | ROS 2 Adapter 的通信契约和领域数据映射，不作为核心领域模型 |

`uran_base` 中已经提出的状态存储、路由目录、协议适配、注册表和结构化核心节点等思路可以保留，但需要重新划分职责：

- 结构化核心节点拆分为普通 C++ `UranRuntime` 和负责 ROS 2 接入的 `Ros2RuntimeHost`，不继续承载各种下行业务处理。
- 协议适配下沉为协议插件，业务消息映射和协议连接解耦。
- 下行处理器归入相应领域服务，核心路由只负责识别和分发。
- 状态存储保留统一视图，但增加所有权和访问边界。
- 包注册进一步抽象为能力注册，使上层依赖能力而不是包名。
- 节点基类能够提供的通用能力，改由 Platform Services API 和轻量 C++ 辅助库提供，避免用户功能继承一个包含过多职责的平台基类。

重构后的核心使用标准 C++ 实现，ROS 2 Adapter 使用 `rclcpp` 完成平台接入。原有 Python/ROS 实现只作为业务行为和接口梳理的参考，不作为新 Runtime 的继承基础。

## 10. 关键运行关系

### 10.1 系统启动

```text
RuntimeHost 启动
    ↓
加载系统、领域和平台装配配置
    ↓
加载平台适配器并注册 Platform Services
    ↓
检查当前部署所需的平台能力
    ↓
创建 UranRuntime、核心组件和领域服务
    ↓
建立设备与组件模型
    ↓
按实例装配并配置所选插件实现
    ↓
激活插件实例并登记能力、状态和协议通道
    ↓
形成设备视图，系统进入运行状态
```

平台适配器加载失败或缺少必要的平台能力时，RuntimeHost 应在业务插件装配前给出明确结果；可选平台能力缺失时可以按装配策略降级。任一业务插件实例失败也不应导致其他实例处于不确定状态。Runtime 记录失败实例及其所属组件，所属领域根据该能力是否为必要依赖决定停止、降级、选择其他提供者或继续运行。

### 10.2 插件切换

```text
领域服务收到能力提供者切换请求
    ↓
检查当前业务状态和安全条件
    ↓
停止使用旧插件实例提供的能力
    ↓
配置并激活新插件实例，或选择已激活的备用实例
    ↓
更新能力、状态和诊断视图
```

如果切换失败，领域服务决定恢复旧实例、保持安全停用或进入降级状态；PluginManager 只负责执行生命周期动作并返回结果。

### 10.3 插件异常

```text
插件实例检测到异常或调用失败
    ↓
更新实例健康状态并上报所属设备与组件
    ↓
领域服务停止使用对应能力
    ↓
尝试重连、选择备用能力提供者或降级运行
    ↓
向业务调用方反馈实际结果
```

异常处理保持在插件、领域服务和 Runtime 三层各自的职责范围内，避免由核心节点集中编写所有设备和业务的恢复分支。

## 11. 架构结论

URAN 重构后的稳定中心不是某个大型核心节点，而是一组边界清晰的公共机制和接口：

```text
UranRuntime 提供平台无关运行机制
        ↓
Platform Adapter 提供机器人操作系统能力
        ↓
领域服务提供统一能力和业务边界
        ↓
业务插件提供可替换的具体实现
        ↓
用户通过平台通信接口、插件 API 或新平台适配器扩展系统
```

设备差异被限制在领域插件中，协议差异被限制在协议领域中，机器人操作系统差异被限制在平台适配层中，任务和业务功能依赖稳定的领域能力。设备、组件、插件实现、插件实例和能力各自拥有清晰的身份与职责；同一个实现可以多实例装配，一个实例可以提供多项能力，一个设备也可以同时使用多条协议通道。

因此，新增组件、设备、协议、算法或用户功能时，主要变化发生在装配配置、业务插件或独立模块内；接入新的机器人操作系统时，主要变化发生在 RuntimeHost、Platform Services 和平台数据映射中。两类扩展互不绑定，核心运行时不因平台替换而重新设计。
