# 插件化架构说明

## 框架化的含义与依赖边界

框架拥有程序装配、执行调度和资源生命周期，扩展通过稳定契约提供能力。本次改造把原先依附 ROS Node 的运行机制提取为独立 `UranRuntime`，宿主注入平台实现；新增插件或替换中间件时，不需要把设备业务写进核心。

| 层 | 代码 | 职责 |
| --- | --- | --- |
| 公共契约 | `src/uran_plugin_api` | 插件接口、身份、状态、消息、平台服务、加载器及持久化接口 |
| 运行时核心 | `src/uran_core_framework` | 装配和生命周期，状态、能力、消息、路由目录、协议网关 |
| Linux 原生平台 | `src/uran_platform_native` | 串行调度/定时器、dlopen 加载器、文件存储、CLI/Unix Socket 宿主 |
| ROS 2 平台 | `src/uran_ros2_adapter` | ROS 日志/时钟、pluginlib 加载器、ROS Topic/Service 管理宿主 |
| 装配 | `config`、`src/uran_bringup` | 独立 YAML 装配、可选 ROS 启动配置 |
| 中立扩展 | `src/uran_core_example_plugins`、`examples/extension` | 通用回环和消息处理示例 |
| 包工具 | `scripts/uran_plugin.py` | 下载、校验、构建、安装、调用宿主管理接口 |

公共 API、核心和通用示例不包含 ROS、pluginlib 或 POSIX SDK 头文件。核心依赖 C++17 标准库、yaml-cpp 和 nlohmann_json；API 只依赖标准库和 yaml-cpp。`tests/test_platform_boundary.py` 检查源码边界。标准库的文件路径、同步原语并不意味着对某个机器人操作系统的依赖。

ROS 适配器当前复用原生串行调度器，因此启用它时也需要 `URAN_BUILD_NATIVE=ON`。这是已提供适配器的实现选择，核心只依赖 `PlatformServices` 抽象。其他平台可替换 `PlatformServices`、`PluginLoader`、`StateStorage` 和宿主。

## 身份、描述与上下文

`PluginDescriptor` 描述实现：`class_type`、`plugin_type`、`plugin_version`、`api_version`。`PluginIdentity` 描述部署实例：`instance_id`、`device_id`、`component_id`。同一个实现可以同时创建多个实例；运行时以实例 ID 唯一标识它们，不能用实现类名代替实例身份。

三个身份字段要求匹配 `[A-Za-z][A-Za-z0-9_]*`，`uran_runtime` 是保留实例 ID。`priority` 数值越大，能力/协议候选选择优先级越高。相同优先级时按实例 ID 稳定排序。

每个实例拥有独立 `PluginContext`：

| 接口 | 能力与约束 |
| --- | --- |
| `platform()` | 绑定实例日志来源、时钟、串行任务、可取消定时器、平台接口清单 |
| `state_access()` | 状态读写与快照；注册、写入、注销绑定当前实例身份 |
| `route_resolver()` | 逻辑别名到语义消息名称的查询，不是 ROS Topic 解析 |
| `messages()` | 通过协议网关上行；覆盖调用者提交的来源身份，停用后拒绝发送 |
| `capabilities()` | 按能力、设备、组件查询可用提供者 |
| `identity()` / `route_scope()` | 实例身份和语义命名作用域 |

`PluginCapabilities.required_interfaces` 用来声明平台服务需求，加载时验证。当前原生平台提供 `log`、`clock.system`、`clock.steady`、`scheduler.serial`、`timer`。`provided_state_fields` 是描述信息，字段实际注册仍由插件执行。

## 生命周期与资源回收

正常过程为创建 → `configure` → `activate` → `deactivate` → `cleanup` → 销毁。`auto_activate: false` 可停留在 configured；停用后可以再次激活；错误实例可查询诊断并重试清理。

1. Loader 创建实例，Manager 验证 API 版本、实现描述、身份及所需平台接口。
2. `configure` 注册状态和读取私有配置。此阶段不允许向实例调度器提交异步任务。
3. `activate` 启用实例服务；成功后注册能力。Runtime 随后绑定协议下行或 `MessagePlugin` 路由。
4. 停用/卸载先移除网关和路由绑定、撤销调度任务，再执行插件生命周期；能力同步移除。
5. 清理成功后撤销状态写权限，回收实例状态登记；即使插件遗漏注销也会回收。Loader 持有动态库直至实例销毁。

实例私有状态通常使用 `plugin.<instance_id>.<field>`。框架绑定的是所有权，不强制所有字段采用这个前缀。停用期间状态保留，便于诊断与重新激活；卸载成功后内存登记撤销。清理失败时实例保留为 error，错误可见，并允许后续重试；不会把失败报告成成功卸载。

启动装配在候选 Session 中执行，全部插件加载、激活、接口绑定、主协议选择成功后才发布会话。配置或加载失败时清理候选。注入持久化后端时，启动阶段写入先暂存，最终成功才提交完整快照；后端提交失败则启动失败。

运行中的单次热加载会回收失败实例的路由、能力和内存状态，但它不是外部副作用事务：插件已经执行的网络发送、文件写入，以及运行中已经成功持久化的状态，不会自动逆转。插件应在自身生命周期中维护资源可回收性。

## 执行线程与插件责任

宿主可从其他线程调用 Runtime，Runtime 将同步请求切换到同一个串行执行器。生命周期、框架触发的消息处理和健康查询在该执行器上执行。协议接收回调可以来自网络线程，网关复制带身份消息，再提交给执行器处理。

Runtime 拒绝在其执行的生命周期、消息或健康等回调中同步重入管理操作。插件通过 `PluginContext` 工作，不获得 Runtime 管理器；不要捕获宿主 Runtime 来同步卸载自身。宿主需要触发后续管理操作时，应在当前回调返回后执行。

实例 `post`/`schedule` 的任务会在停用时撤销。取消是幂等的，释放等待执行的闭包；从执行器外取消正在执行的任务会等待它返回。宿主必须先停止/销毁 Runtime，再从宿主线程销毁 Platform，不能先关调度器，也不能在其工作线程销毁 Platform。

插件自行创建的线程、第三方网络回调、文件句柄等仍须由 `deactivate`/`cleanup` 停止并回收。耗时工作不能阻塞串行回调。该版本使用进程内 C++ 插件，隔离异常和资源作用域，不提供进程崩溃隔离、抢占式超时或硬实时保证。

## 消息、能力与协议

`MessagePlugin` 是 `Plugin` 的可选特化，通过 `message_types()` 和 `handle(DownlinkEnvelope)` 接收通用消息。普通 Plugin 不必实现消息接口；协议插件实现 `ProtocolPlugin`。协议插件负责在 `activate` 中建立连接，在 `deactivate` 中断开；框架不额外重复调用 connect/disconnect。

下行消息包含 `message_type`、`payload`、`correlation_id`、`source` 和 `target`。`payload` 为字符串，由扩展定义语义；JSON 管理宿主会编码为 JSON。核心不定义设备运控指令。

- 显式目标可按设备、组件、实例、能力组合筛选，所有已填写条件同时满足；类型精确匹配，再选择优先级最高的处理者。
- 无目标消息不会任意投递给某个实例，只匹配全局处理器，或进入宿主的未处理消息回调。
- 找不到目标时，宿主的未处理回调可能接收并报告成功；这表示完成转交，不表示任何设备命令已执行。
- 来源身份由网关绑定的协议实例覆盖，不能信任载荷里的同名字段。每次绑定有独立代次，解绑前保存的回调、排队后才到达的旧代次消息不会投递到新绑定。
- 上行选择顺序为指定协议 → 主协议 → 其余实例优先级排序，发送失败则继续候选。插件上行来源固定，候选限定同一设备；宿主直接上行无设备限定，是受信任的管理入口。
- 选路按显式 target 执行，不包含来源到目标的授权策略；跨设备访问规则应由接入适配层或后续策略扩展定义。

`RouteCatalog` 只提供别名查询，例如 `echo: example.echo`。名称由字母开头的段组成，用点连接；`/uran/...` 这类平台路径被拒绝。它不会自动改写消息，插件或宿主需要显式调用 resolver。

## 状态与持久化

状态字段具有名称、类型、单位、所有者和持久化标记。字段重复登记必须保持定义一致，只有所有者可以写入或注销；实例包装器同时检查调用来源，阻止冒充其他实例。宿主写入使用 `external.*` 来源，无法覆盖已有插件/系统字段。

支持 JSON 类型校验和带来源、时间戳的值，快照导出保留 JSON 类型。未登记扩展字段第一次写入时确定所有者。内部 StateStore 支持变更订阅，回调在锁外执行并隔离异常；公共插件 StateAccess 当前提供读写和快照，不承诺通用事件总线。

持久化由 `StateStorage` 注入。原生实现使用临时文件、fsync 与 rename 替换完整 JSON 快照；正常重启恢复字段定义、所有权和值。写入失败不会提交内存值或发出变更通知。没有配置后端时，请求持久化明确失败。

一旦字段持久化，后续更新也保持持久化。卸载只撤销当前内存登记，持久化记录继续保存，以便相同身份和定义重新注册；当前没有持久化字段迁移/删除管理接口。插件在 configure 中无条件赋默认值会覆盖恢复值，应先 get 再初始化。

## ABI 与平台迁移

公共 API 版本为 `2.0`，原生导出符号为 `uran_plugin_export_v2`，导出结构中的 ABI 版本为 `2`。每个原生动态库导出一个类；一个包可以含多个动态库。原生 C 入口用于发现工厂，实际对象仍使用 C++ 虚接口、STL 和 yaml-cpp，因此需使用兼容的编译器、标准库和依赖版本，不能将版本号检查视为跨工具链二进制兼容保证。

原生 Loader 读取 JSON manifest，ROS Loader 使用 pluginlib 的 XML/ament 索引。中立示例通过独立 ROS 导出包装类在 ROS 宿主中使用，通用实现不链接 pluginlib。Python 当前承担包管理和宿主管理客户端，不内嵌 Python 解释器，也没有 Python PluginLoader。
