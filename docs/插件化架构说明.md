# URAN C++ 插件化软件架构说明

本文档描述 URAN 重构后的软件架构，重点说明系统分层、模块职责、插件机制、通信关系和二次开发接口。文档不预先固化 Topic 名称、消息字段、QoS 参数、配置格式等实现细节，这些内容在具体接口设计中按业务语义确定。

核心运行时和进程内插件采用 C++ 实现；ROS 2 节点及通信能力通过 `rclcpp` 接入，不再使用 Python/`rospy` 体系作为核心架构实现。

---

## 1. 总体架构

URAN 采用“核心运行时 + 领域服务 + 插件实现 + 用户扩展”的结构。核心运行时提供稳定的公共机制，领域服务组织业务能力，插件封装设备、协议和算法差异，用户通过公开接口添加功能。

```text
┌──────────────────────────────────────────────────────────┐
│                      用户扩展                            │
│  独立功能包 / 业务节点 / 第三方领域插件 / 外部系统适配   │
└────────────────────────────┬─────────────────────────────┘
                             │ 公共 ROS 2 接口 / 插件 API
┌────────────────────────────▼─────────────────────────────┐
│                      领域服务层                          │
│       运控 / 媒体 / 传感器 / 任务 / 协议 / 存储         │
└────────────────────────────┬─────────────────────────────┘
                             │ Runtime 公共能力
┌────────────────────────────▼─────────────────────────────┐
│                      URAN Runtime                        │
│ 插件管理 / 配置 / 状态 / 路由 / 能力注册 / 事件 / 诊断  │
└────────────────────────────┬─────────────────────────────┘
                             │
┌────────────────────────────▼─────────────────────────────┐
│               ROS 2、设备接口和系统基础设施              │
└──────────────────────────────────────────────────────────┘
```

各层职责如下：

- **Runtime** 只提供通用运行机制，不包含设备型号判断、业务流程或协议业务字段解析。
- **领域服务** 负责某一类能力的统一语义、协调逻辑和安全边界。
- **插件** 负责实现一个明确的变化点，例如设备适配、协议传输、格式转换或任务执行。
- **用户扩展** 通过公开 ROS 2 接口或插件 API 接入，不直接依赖 Runtime 内部类。

依赖方向保持从具体实现指向稳定抽象：

```text
具体设备、协议和用户实现
            ↓
        领域插件 API
            ↓
       Runtime 公共 API
            ↓
          ROS 2
```

Runtime 不反向依赖任何具体插件，领域之间也不通过对方的内部对象进行耦合。

## 2. 核心运行时

Runtime 是系统公共能力的承载层，其主要组件如下：

```text
UranRuntime
├── RuntimeNode          ROS 2 节点与组件装配
├── PluginManager       插件发现和生命周期管理
├── ConfigManager       配置加载与配置快照
├── StateStore          统一状态空间
├── RouteManager        ROS 2 通信端点组织
├── CapabilityRegistry  能力注册与查询
├── EventDispatcher     进程内事件通知
└── DiagnosticsManager  健康状态与诊断汇总
```

这些组件均面向抽象接口工作。具体部署时可以合并在一个 Runtime 包中，也可以根据规模拆成多个包；组件边界比包的数量更重要。

### 2.1 RuntimeNode

RuntimeNode 是核心运行时的装配入口，负责创建公共组件、连接组件依赖、建立 ROS 2 通信端点并驱动系统启动和停止。

RuntimeNode 不直接实现具体业务。收到外部消息后，它只完成接口适配和分发，将业务处理交给相应领域服务；需要对外发布数据时，也由领域服务或协议网关生成业务结果，RuntimeNode 负责接入 ROS 2 运行环境。

### 2.2 PluginManager

PluginManager 统一管理进程内 C++ 插件，主要承担：

- 发现并创建插件实例。
- 判断插件类型和接口兼容性。
- 向插件注入受控的运行上下文。
- 驱动配置、激活、停用和清理过程。
- 维护插件实例、能力和健康状态。
- 在加载或运行异常时隔离故障并反馈给所属领域。

PluginManager 只管理通用生命周期，不决定运动控制、任务切换等领域行为。涉及业务安全的插件切换由对应领域服务发起和裁决。

### 2.3 PluginContext

PluginContext 是插件访问平台能力的统一入口，用于替代插件对 Runtime 内部组件的直接依赖。它可以向插件提供：

- ROS 2 节点相关能力。
- 日志、时钟和定时能力。
- 插件自身配置视图。
- 受权限控制的状态读写。
- 通信端点解析和创建辅助能力。
- 事件、诊断和健康信息上报入口。
- 领域服务明确开放的其他能力。

Context 只暴露稳定接口，不暴露 PluginManager、StateStore 等组件的具体实现对象。这样 Runtime 内部实现可以调整，而不影响第三方插件。

### 2.4 ConfigManager

ConfigManager 将系统配置、领域配置和插件私有配置组织为独立配置空间，并向使用者提供经过校验的配置快照。

配置架构需要能够表达配置来源、结构校验、版本、更新范围和失败恢复方式，但不在本架构文档中规定具体文件格式。插件只能访问分配给自己的配置，避免插件之间共享和修改无关配置。

### 2.5 StateStore

StateStore 提供统一运行状态视图，用于承载系统、设备、网络、控制、运动、媒体、任务、插件等状态。它解决的是状态所有权和跨模块访问问题，而不是替代所有业务数据通道。

状态模型需要能够描述字段所有者、数据类型、来源、时间信息、读写范围以及是否需要变化通知。核心字段由平台或领域服务维护，插件扩展状态位于各自命名空间，不能覆盖其他模块的状态。

高频传感器流、图像流和大数据内容仍通过合适的 ROS 2 通道传输，不写入通用状态空间。

### 2.6 RouteManager

RouteManager 负责集中组织 Runtime 使用的 Topic、Service、Action 和命名空间关系，使模块依赖通信语义而不是散落的字符串。

它提供的是路由解析和接口组织能力，不负责预先生成所有通信端点。公共接口、领域接口和插件私有接口分别由对应的接口设计确定，Runtime 只按配置和接口描述建立连接。

### 2.7 CapabilityRegistry

CapabilityRegistry 记录当前系统实际可用的能力及其提供者。例如系统可以登记运动、拍照、定位、某类传感器、某类任务执行器或某种上行协议能力。

领域服务和插件在激活后注册能力，在停用或故障时撤销或降级能力。任务和用户扩展通过能力查询选择可用服务，不需要识别具体设备型号或插件类名。

### 2.8 EventDispatcher 与 DiagnosticsManager

EventDispatcher 用于同一进程内的低耦合事件通知，例如插件状态变化、配置变化和连接状态变化。它不替代 ROS 2；需要跨进程、跨节点或供外部观察的事件仍通过公共 ROS 2 接口发布。

DiagnosticsManager 汇总 Runtime、领域服务和插件的生命周期、外部依赖、错误和降级状态，形成统一的系统健康视图。具体诊断字段由后续接口设计确定。

## 3. 插件架构

插件用于封装系统中经常变化、需要替换或由第三方提供的实现。插件不等同于所有功能；稳定的领域协调逻辑仍保留在领域服务中。

### 3.1 插件类型

| 插件类型 | 主要职责 | 典型实现 |
|---|---|---|
| 协议插件 | 外部连接、收发、编解码适配和连接状态 | MQTT、WebSocket、专有协议 |
| 运控插件 | 统一运动语义与设备原生控制接口之间的适配 | 轮式底盘、机器狗、无人机适配 |
| 媒体插件 | 媒体源、转换、编码或传输的具体实现 | 相机源、编码器、RTSP/WebRTC 传输 |
| 传感器插件 | 原始数据接入、格式与坐标转换 | 气体、温湿度、雷达等适配 |
| 任务插件 | 可插拔的任务类型或任务执行器 | 巡检、拍照、路线执行、算法任务 |
| 存储插件 | 状态、事件或业务数据的持久化实现 | 本地文件、数据库、远程存储 |

插件类型可以扩展，但每类插件应由相应领域 API 定义能力，不使用一个包含所有业务方法的通用“大插件接口”。

### 3.2 接口组成

插件接口分为两部分：

1. **基础接口**：描述插件身份、接口版本、生命周期、能力和健康状态。
2. **领域接口**：描述插件在所属领域提供的操作，例如发送协议数据、执行运动命令、读取传感器或运行任务。

基础接口保证 PluginManager 能够统一管理插件，领域接口保证业务调用保持类型清晰。第三方插件只依赖公共 API 包，不依赖 Runtime 实现包。

### 3.3 生命周期

插件生命周期采用统一状态模型：

```text
发现 → 创建 → 配置 → 激活 → 运行
                    │       │
                    └── 停用 ──→ 清理/卸载
```

- **创建**：建立插件对象，不连接外部设备。
- **配置**：读取配置，准备通信对象和内部资源。
- **激活**：连接设备或外部系统，开始提供能力。
- **停用**：停止输出、异步任务和外部交互。
- **清理**：释放线程、句柄、通信对象和其他资源。

生命周期的具体函数形式由插件 API 定义。架构只要求 PluginManager 能够控制资源边界，并获得明确的成功、失败和健康结果。

### 3.4 发现与加载

C++ 进程内插件通过 ROS 2 `pluginlib`/`class_loader` 发现和加载。插件描述用于关联实现类、插件类型和公共 API，不把业务配置写入插件描述文件。

插件选择和插件参数由系统装配配置提供。更换设备或协议时，领域服务仍依赖相同的领域 API，只改变所选插件和对应配置。

### 3.5 故障隔离与运行形态

插件边界首先解决代码依赖和实现替换问题，并不天然提供进程级故障隔离。模块采用哪种运行形态，应根据稳定性和资源特征决定：

- 需要低延迟、直接调用和统一生命周期的实现，可作为进程内 C++ 插件。
- 资源消耗较大、可能阻塞、来源不受控或需要独立重启的实现，适合作为独立 ROS 2 节点。
- 需要单独部署和升级的完整业务能力，适合作为独立功能包。

两种形态尽量使用同一套领域数据模型和通信语义，使进程内实现与独立节点实现可以替换。

## 4. 领域服务

领域服务位于 Runtime 与具体插件之间。它负责稳定的业务语义、能力编排和领域安全，避免这些逻辑散落到设备插件或协议插件中。

### 4.1 协议领域

协议领域由协议网关和协议插件组成：

```text
外部连接
    ↓
协议插件：连接、收发、重连、传输级编解码
    ↓
协议网关：平台消息封装、上下行选择、失败切换
    ↓
领域路由
```

协议插件不处理运动、任务、媒体等业务逻辑。外部协议发生变化时，只影响协议领域和必要的映射层，不影响其他业务节点。

### 4.2 运控领域

```text
统一运动请求
      ↓
控制权、状态和安全检查
      ↓
运控服务
      ↓
运控插件
      ↓
设备原生控制接口
```

运控服务负责统一命令语义、控制权、限速、超时、急停和执行反馈；运控插件只负责统一命令与设备原生接口之间的转换。

任务模块和用户业务不直接调用设备运控插件，而是通过运控领域公开的能力发起请求。

### 4.3 媒体领域

媒体领域将媒体源、转换、编码、传输和会话管理分开：

```text
媒体源 → 格式转换 → 编码 → 传输
   └──────────── 媒体会话管理 ────────────┘
```

相机型号、编码方式和传输协议因此可以独立替换。媒体会话由领域服务统一管理，插件只实现其中一个明确环节或一组紧密相关的能力。

### 4.4 传感器领域

```text
设备原始数据
      ↓
数据源适配
      ↓
格式、单位和坐标转换
      ↓
标准领域数据
      ↓
ROS 2 接口 / 状态摘要 / 上层算法
```

传感器领域负责形成稳定的数据语义，具体设备消息和厂商 SDK 保留在插件内部。状态空间只保存需要共享的状态或摘要，不承载完整高频数据流。

### 4.5 任务领域

任务领域负责任务实例的创建、执行、反馈、暂停、恢复、取消和结果管理。任务插件实现具体任务类型，任务服务负责任务状态机和能力协调。

任务执行需要运动、媒体、定位或传感器能力时，通过对应领域服务申请，不持有具体插件对象。这样设备插件替换不会迫使任务实现同步修改。

## 5. 通信与数据流

### 5.1 下行流程

```text
云端或外部系统
      ↓
协议插件接收数据
      ↓
协议网关转换为平台消息
      ↓
消息路由识别目标领域
      ↓
领域服务进行校验、状态判断和业务处理
      ↓
领域插件或独立功能节点执行
      ↓
结果进入统一反馈链路
```

协议层只负责接入和转换，路由层只负责分发，领域服务负责业务判断，插件负责具体执行。

### 5.2 上行流程

```text
设备、插件或业务节点产生数据
      ↓
领域服务形成平台数据
      ↓
上行网关选择可用协议
      ↓
协议插件完成外部发送
      ↓
发送结果和连接状态进入诊断与状态视图
```

同一领域数据可以通过不同协议发送，业务节点不需要感知当前使用 MQTT、WebSocket 或其他传输方式。

### 5.3 模块间交互方式

模块间根据边界选择交互方式：

- 同一进程、低开销且不需要对外暴露的调用，可使用 C++ 接口或内部事件。
- 跨节点、跨进程、需要独立部署或需要被外部观察的交互，使用 ROS 2 通信。
- 持续数据和状态、短时请求、长时间可取消任务分别采用符合其语义的 ROS 2 通信机制。

架构不强制所有功能都插件化，也不强制所有内部交互都经过 ROS 2。选择依据是模块边界、部署需求和故障隔离需求。

### 5.4 需要进一步约定的通信内容

公共接口和领域接口在落地时需要分别说明：

- 接口的业务语义、方向和所有者。
- 数据模型、单位、时间和坐标语义。
- 调用结果、异常和取消方式。
- 接口版本及兼容方式。
- 根据控制、状态、高频数据等不同语义选择合适的 QoS。
- 多设备、多实例部署时的命名空间关系。

具体 Topic 名称、Service/Action 定义和 QoS 参数由对应领域的接口说明给出，本架构文档不提前固定。

## 6. 状态、配置和诊断关系

状态、配置和诊断是三个不同的视图：

- **配置** 表达系统期望如何运行，例如启用哪些插件以及插件参数。
- **状态** 表达系统当前处于什么状态，例如当前协议、控制模式和任务阶段。
- **诊断** 表达模块是否健康以及出现了什么问题，例如连接失败、插件降级或处理超时。

三者由 Runtime 统一提供访问机制，但内容所有权仍属于产生它们的组件。领域服务维护领域状态，插件维护自身运行状态，Runtime 负责汇总和对外提供统一视图。

配置更新不直接修改状态；配置应用成功后，由实际执行组件更新运行状态。诊断也不代替业务结果，业务调用应通过本身的返回或反馈接口给出结果。

## 7. 二次开发接口

URAN 对外提供两类主要扩展方式。

### 7.1 独立 ROS 2 功能包

适用于业务节点、算法接入、数据处理、任务编排和需要独立部署的功能。开发者通过公共 Message、Service、Action、状态和能力接口与 URAN 交互。

独立功能包不需要链接 Runtime 实现，也不访问插件实例。只要公共通信契约保持兼容，功能包可以独立编译、启动和升级。

### 7.2 C++ 领域插件

适用于设备驱动适配、协议实现、传感器转换、运动控制、媒体处理和任务执行器等需要嵌入领域服务的能力。

插件开发者只需依赖公共插件 API 和对应领域 API，实现领域能力并通过 `pluginlib` 导出。插件的实例化、配置、启停、状态和诊断由 Runtime 统一接管。

### 7.3 可用扩展面

| 扩展面 | 用途 |
|---|---|
| 公共 ROS 2 接口 | 接入独立节点、算法和外部业务功能 |
| 领域插件 API | 嵌入设备、协议、媒体、传感器或任务实现 |
| 能力注册接口 | 声明插件或节点可提供的能力 |
| 扩展状态接口 | 提供插件和用户功能的运行状态 |
| 配置入口 | 注入用户功能或插件自己的配置 |
| 事件与诊断入口 | 报告运行变化、健康状态和错误 |

这些扩展面共同构成用户接口。开发者不需要修改 Runtime，也不需要依赖其他具体插件。

### 7.4 扩展边界

用户扩展可以新增能力，但不能绕过领域服务直接修改其他模块状态、替换安全决策或持有 Runtime 内部管理器。涉及运动、控制权和设备安全的操作始终经过对应领域服务。

如果用户功能只消费或生产平台数据，优先作为独立 ROS 2 功能包；只有确实需要嵌入领域执行链路、共享生命周期或降低调用开销时，才设计为进程内插件。

## 8. 代码与部署组织

软件包按职责可归纳为四类逻辑模块：

```text
公共接口
├── ROS 2 消息、服务和动作
├── Runtime 公共模型
└── 各领域插件 API

核心运行时
├── Runtime 装配
├── 插件、配置、状态和路由
└── 能力、事件和诊断

领域模块
├── 协议、运控、媒体、传感器和任务服务
└── 各领域公共数据模型

具体实现
├── 设备和协议插件
├── 用户插件
└── 独立业务功能包
```

实际工程可以根据维护团队和部署方式拆分 ROS 2 包，不要求每个逻辑组件对应一个包。无论如何拆分，应保持以下依赖关系：

- 公共 API 不依赖 Runtime 或具体实现。
- Runtime 只依赖公共 API 和基础设施。
- 领域服务依赖 Runtime 公共能力和领域 API。
- 具体插件依赖相应 API，不反向成为核心依赖。

部署时，可以将稳定且紧密协作的领域服务和插件组合在一个进程，也可以把媒体、第三方算法或高风险模块放到独立进程。部署形态变化不应改变领域语义和用户接口。

## 9. 与现有工程的对应关系

现有 `uran_ws` 中的功能可以按下表映射到新架构：

| 现有模块 | 重构后的主要归属 |
|---|---|
| `uran_core` | Runtime 装配、状态与配置、路由、协议网关、诊断 |
| `uran_move` | 运控领域服务和设备运控插件 |
| `uran_media` | 媒体领域服务及媒体源、编码、传输实现 |
| `uran_autotask` | 任务领域服务和具体任务执行器 |
| `uran_msgs` / `uran_srvs` | 公共 ROS 2 通信契约，并按需要补充 Action 或领域接口 |

`uran_base` 中已经提出的状态存储、路由目录、协议适配、注册表和结构化核心节点等思路可以保留，但需要重新划分职责：

- 结构化核心节点收敛为 Runtime 装配入口，不继续承载各种下行业务处理。
- 协议适配下沉为协议插件，业务消息映射和协议连接解耦。
- 下行处理器归入相应领域服务，核心路由只负责识别和分发。
- 状态存储保留统一视图，但增加所有权和访问边界。
- 包注册进一步抽象为能力注册，使上层依赖能力而不是包名。
- 节点基类能够提供的便利能力，改由公共 ROS 2 接口和轻量 C++ 辅助库提供，避免用户功能继承一个包含过多职责的基类。

重构后的核心实现采用 C++/`rclcpp`。原有 Python 版本可以作为业务行为和接口梳理的参考，不作为新 Runtime 的继承基础。

## 10. 关键运行关系

### 10.1 系统启动

```text
Runtime 创建
    ↓
加载系统与领域配置
    ↓
创建核心组件和领域服务
    ↓
发现并配置所选插件
    ↓
领域服务检查依赖和能力
    ↓
激活插件并注册可用能力
    ↓
系统进入运行状态
```

任一插件失败不应导致所有插件处于不确定状态。Runtime 记录失败，所属领域根据该插件是否为必要依赖决定停止、降级或继续运行。

### 10.2 插件切换

```text
领域服务收到切换请求
    ↓
检查当前业务状态和安全条件
    ↓
停止旧插件提供能力
    ↓
配置并激活新插件
    ↓
更新能力、状态和诊断视图
```

如果切换失败，领域服务决定恢复旧插件、保持安全停用或进入降级状态；PluginManager 只负责执行生命周期动作并返回结果。

### 10.3 插件异常

```text
插件检测到异常或调用失败
    ↓
更新插件健康状态并上报诊断
    ↓
领域服务停止使用对应能力
    ↓
尝试重连、备用插件或降级运行
    ↓
向业务调用方反馈实际结果
```

异常处理保持在插件、领域服务和 Runtime 三层各自的职责范围内，避免由核心节点集中编写所有设备和业务的恢复分支。

## 11. 架构结论

```text
Runtime 提供运行机制
        ↓
领域服务提供统一能力和业务边界
        ↓
插件提供可替换的具体实现
        ↓
用户通过 ROS 2 接口或插件 API 扩展系统
```

设备差异限制在设备插件中，协议差异限制在协议领域中，任务和业务功能依赖稳定的领域能力。这样新增设备、协议、算法或用户功能时，主要变化发生在独立插件或功能包内，不需要继续修改核心运行时。
