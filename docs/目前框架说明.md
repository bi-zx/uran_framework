# URAN 当前 ROS 2 原型框架说明

## 1. 当前范围

当前 `uran_rebuild` 是用来验证插件生命周期、多实例、状态隔离、能力注册和多协议装配关系的 ROS 2 原型。它已经把若干运行机制拆成独立 C++ 组件，但尚未完成“平台无关核心 + 可替换平台适配器”的目标拆分，因此不能把当前代码视为最终架构。

已经提供：

- `rclcpp` Runtime 节点。
- 配置快照管理器。
- 线程安全状态空间。
- 路由目录。
- 公共插件基类。
- 协议插件基类。
- `pluginlib` 插件管理器。
- 多协议网关和消息路由器。
- 插件生命周期和异常边界。
- 插件实现描述与运行实例身份分离。
- 设备、组件和插件实例的归属模型。
- 同一插件实现类的多实例装配。
- 按设备、组件和能力查询提供者的 `CapabilityRegistry`。
- 插件能力随激活、停用和卸载自动登记或撤销。
- 插件状态写权限与运行实例标识绑定。
- 插件清理时受控注销实例状态字段。
- 协议实例优先级、主通道和失败回退。
- 下行消息来源协议实例识别。
- 回环协议示例插件。
- bringup 配置和 launch 文件。
- 配置、状态空间、能力注册、路由、消息分发、协议网关和双实例隔离测试。

当前未实现：

- 真实 MQTT/WebSocket 网络连接。
- 云端 JSON 与领域消息的正式编解码。
- 最终 URAN Message、Service 和 Action。
- 状态持久化后端。
- 运控、媒体、传感器和任务领域服务。
- 具体机器人设备适配。
- 对外设备注册快照及其正式协议映射。
- 运行中的动态增删插件和协议网关热更新入口。

### 与现有 `uran_core` 的对应关系

| 现有职责 | 新框架中的承载位置 |
|---|---|
| `core.yaml`、`network.yaml` 配置读取 | `ConfigManager` 与 bringup 配置 |
| `StateManager` 状态读写和变化通知 | `StateStore` 与 `ScopedStateAccess` |
| MQTT 连接和上下行 | `ProtocolPlugin`、`ProtocolGateway`；真实 MQTT 实现留给独立插件 |
| 按消息类型分发下行指令 | `MessageRouter`；具体业务处理留给后续领域模块 |
| 状态广播、心跳和主动上报 | `RuntimeNode` 的占位 ROS 2 端点和定时器 |
| 固定 Topic/Service 创建 | `RouteCatalog` 与 Runtime 装配层 |

该映射说明的是当前原型如何承接旧工程功能。它保留了原有核心功能的承载位置，但不复制原节点中的大段业务分支。

## 2. 运行关系

当前原型的实际运行关系如下，其中 Runtime、插件加载和通信接入仍处在同一个 ROS 2 实现边界内：

```text
uran_bringup
     │ 加载配置
     ▼
RuntimeNode
├── ConfigManager
├── StateStore
├── RouteCatalog
├── CapabilityRegistry
├── MessageRouter
├── ProtocolGateway
└── PluginManager
      │ pluginlib：同一实现创建多个实例
      ├── protocol_primary
      └── protocol_backup
```

Runtime 与具体插件实现之间没有编译期依赖。`uran_bringup` 负责选择需要加载的插件，插件包通过 pluginlib 描述文件向 Runtime 声明实现类。这解决了具体业务实现的替换问题，但尚未解决 Runtime 对 ROS 2 平台的依赖。

公共插件接口位于 `uran_plugin_api`。第三方插件不需要依赖 `uran_core_framework` 的具体实现，但当前 `uran_plugin_api` 自身仍依赖 `rclcpp`，所以它还不是目标架构中的平台无关插件 API。

### 身份模型与多实例

当前框架已经将插件实现信息和运行实例身份拆开：

```text
插件实现
  描述：实现类型、实现版本、API 版本、导出类名
              │
              │ 同一实现可创建多个实例
              ▼
插件实例
  描述：实例标识、所属设备、所属组件、命名空间和私有配置
```

例如 `LoopbackProtocolPlugin` 在 bringup 中被创建为 `protocol_primary` 和 `protocol_backup` 两个实例。两个实例属于同一设备的通信组件，但拥有不同配置、优先级、状态字段和生命周期。PluginManager 的索引、生命周期操作和状态所有权均以 `instance_id` 为准，不再要求实现类返回固定实例标识。

当前 `PluginContext` 向每个实例提供：

- `instance_id`：当前运行对象的唯一标识。
- `device_id`：实例所属设备。
- `component_id`：实例所属逻辑组件。
- 实例自己的 ROS 命名空间和受控状态访问入口。

插件类的 `descriptor()` 只描述实现类型、实现版本、API 版本和导出类名，不包含部署现场身份。
如果装配配置没有显式提供 `ros_namespace`，PluginManager 会按“Runtime 基础命名空间/设备/组件/实例”生成默认命名空间，使同一实现类的多个实例不会自然落入同一个 ROS 命名空间。这是当前 ROS 2 原型的装配方式；目标架构将先生成平台无关的路由作用域，再由 ROS 2 Adapter 映射为 ROS Namespace。

## 3. 与目标平台无关架构的差距

当前原型已经验证了业务插件化的部分核心机制，但机器人操作系统仍被写入公共 API 和核心实现。主要差距如下：

| 当前实现 | 目标调整 |
|---|---|
| `RuntimeNode` 继承 `rclcpp::Node` | 提取普通 C++ `UranRuntime`，由 `Ros2RuntimeHost` 持有 Node 与 Executor |
| `PluginContext` 暴露 `rclcpp::Node` | 只暴露日志、时钟、定时、调度和通信等 Platform Services 接口 |
| `PluginManager` 直接持有 `pluginlib::ClassLoader` | 拆分生命周期管理与 `PluginLoader`，将 pluginlib 放入 ROS 2 Loader 后端 |
| `RouteCatalog` 保存平台端点字符串 | 核心改为面向设备、组件、能力和消息类型的语义路由，端点映射归平台适配器 |
| 公共 API 和核心包使用 `ament_cmake`、`rclcpp` | 平台无关部分使用标准 C++/CMake，可在无 ROS 环境编译测试 |
| 占位通信接口由 RuntimeNode 直接创建 | 由 ROS 2 Adapter 创建端点并完成 ROS 消息与领域数据模型的转换 |

目标拆分关系为：

```text
现有 RuntimeNode
├── UranRuntime             平台无关状态、配置、能力、语义路由和领域装配
└── Ros2RuntimeHost         ROS 2 节点、Executor、端点和数据转换

现有 PluginManager
├── PluginManager           平台无关实例与生命周期管理
└── Ros2PluginLoader        基于 pluginlib 的对象发现和创建

现有 PluginContext
├── 平台无关实例身份和受控 Runtime 服务
└── Platform Services       由当前 RuntimeHost 注入具体实现
```

因此，当前代码应被视为 ROS 2 RuntimeHost 的原型和基础机制验证。后续重构需要提取平台无关层，而不是在现有 `RuntimeNode` 上继续叠加其他机器人操作系统的条件分支。

## 4. 插件生命周期

```text
创建实例
   ↓
configure
   ↓
activate
   ↓
deactivate
   ↓
cleanup
   ↓
释放实例
```

PluginManager 在调用插件方法时不会持有内部管理锁，避免插件回调 Runtime 后形成锁重入。生命周期方法抛出的异常会被拦截并转换为状态结果。

批量加载插件时，如果某一插件配置或激活失败，PluginManager 会按相反顺序清理本次已经加载的插件。

插件激活成功后，PluginManager 读取插件声明的能力并登记到 CapabilityRegistry；停用、卸载或激活回滚时撤销该实例的全部能力。能力登记失败时，实例不会被标记为可用，并会尽力回到停止状态。

## 5. 状态空间

StateStore 支持：

- 注册状态字段及所有者。
- 由字段所有者注销状态定义和值。
- 校验字段名称和 JSON 值。
- 控制已注册字段的写入来源。
- 扩展字段首次写入时绑定所有者。
- 生成保持 JSON 类型的状态快照。
- 订阅状态变化。
- 并发读取和独占写入。

PluginManager 为每个插件实例创建独立的 `ScopedStateAccess`。插件注册状态字段时可以省略所有者，受控视图会自动绑定当前 `instance_id`；写入或注销时若伪造其他来源，请求会被拒绝。

示例插件按照实例生成状态字段，例如 `plugin.protocol_primary.connected` 和 `plugin.protocol_backup.connected`。停用其中一个实例不会改变另一个实例的连接状态，清理实例时会移除该实例注册的状态字段。

状态变化回调在状态锁外执行，因此回调可以再次读取 StateStore。
单个状态观察者抛出的异常会被隔离，不会改变已经提交的状态，也不会阻断其他观察者。

持久化标记目前只保存在状态元数据中，后续应通过 `StoragePlugin` 或独立持久化服务完成落盘。

## 6. 占位接口

RuntimeNode 当前使用 `std_msgs/msg/String` 提供状态写入、状态快照和心跳通道。这些通道只用于验证 ROS 2 原型的装配关系，不应直接作为正式业务接口发布，也不属于平台无关核心的数据模型。

正式接口确定后，ROS 2 Adapter 应在独立接口包中定义 ROS 通信契约，并将其转换为平台无关的领域数据模型，再调用 UranRuntime、StateStore 和领域服务。更换 ROS 消息类型或接入其他平台时，不应修改核心组件。

## 7. 当前原型中新增协议插件

按当前 ROS 2 原型实现一个协议插件需要：

1. 继承 `uran_plugin_api::ProtocolPlugin`。
2. 实现公共生命周期。
3. 实现 `connect()`、`disconnect()` 和 `publish()`。
4. 保存并调用 `DownlinkCallback`。
5. 使用 `PLUGINLIB_EXPORT_CLASS` 导出为 `uran_plugin_api::Plugin`。
6. 在 `plugin_description.xml` 中声明实现。
7. 在 bringup 插件配置中选择实现类。

这里生成和导出的是“插件实现类”，不是某个现场运行实例。设备标识、组件标识、实例标识、地址和端口等部署信息由 bringup 装配配置提供；同一实现类可以在配置中出现多次并形成多个独立实例。

以上步骤只适用于当前 ROS 2 Loader。目标架构中的通用插件应通过 `PluginLoader` 契约导出，不直接依赖 pluginlib；只有 ROS 2 专用插件或 ROS 2 Loader 后端保留上述平台依赖。

网络库回调通常运行在独立线程。当前实现可通过线程安全队列或 ROS 2 调度机制送入 Runtime；目标架构应改为通过平台无关调度服务进入 UranRuntime，避免网络线程直接修改 Runtime 内部状态，也避免协议插件依赖某个平台的执行器。

## 8. 当前 ROS 2 装配示例

bringup 中的示例配置表达一台设备、一个通信组件和两个协议实例：

```yaml
default_device_id: robot_001
primary_protocol_instance: protocol_primary

plugins:
  - instance_id: protocol_primary
    component_id: communication
    plugin_type: protocol
    class_type: uran_core_example_plugins/LoopbackProtocolPlugin
    priority: 100
    config:
      channel: primary

  - instance_id: protocol_backup
    component_id: communication
    plugin_type: protocol
    class_type: uran_core_example_plugins/LoopbackProtocolPlugin
    priority: 50
    config:
      channel: backup
```

`default_device_id` 可由单个插件项中的 `device_id` 覆盖。`primary_protocol_instance` 指向运行实例；未显式指定时，网关从已注册实例中选择优先级较高者。上行发送可以指定首选协议实例，失败后再按主实例和其他实例进行回退。

当前 Runtime 在初始化阶段一次性建立 PluginManager、CapabilityRegistry 和 ProtocolGateway 的候选对象，全部成功后再提交，避免插件或协议只注册一半。运行时动态增删实例尚未对外开放；后续增加该能力时，需要继续保持三者同步更新。
