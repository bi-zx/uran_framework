本记录对应《受控部署与 Bootstrap》的设备端 v1 实现。验证在本地 Ubuntu 22.04.5 LTS、Linux x86_64、Python 3.13 环境进行，没有连接或修改 CyberDog2，也没有通过 SSH 进行部署。

部署测试验证了以下行为：

- 从安装后的 SDK 和私有 Python 依赖制作、验签、安装统一 bootstrap，不依赖相邻源码仓库。
- agent、用户批准者、发布者分离签名；验证请求的设备、有效期和授权范围；拒绝被撤销、过期或绑定其他请求的授权。
- 由 MQTT 经真实 Core 路由部署任务，持久化执行并通过原有上行包装上报最终状态。
- 整套发行物下载、暂存校验、只读发布、依赖服务管理、业务先配置后激活、原子提交。
- 健康检查失败后恢复旧发行物和文件状态；监督进程被强制终止后恢复未完成事务。
- 最后提交的发行物损坏时启动空管理 Core，并通过同一 Core 管理入口在线提交修复版本。
- 请求幂等、并发拒绝、安全取消、不可变发行 ID、声明式文件状态迁移和明确恢复快照的回滚。
- 恶意归档、错误摘要、未授权下载 origin、部分下载恢复、后台后代进程清理。
- 默认关闭维护通道；具体用户授权下启用测试 provider，过期或撤销后关闭；一次性 HTTPS 注册和禁止注册跳转。
- bootstrap 拒绝不匹配的 Python/系统发行版，以及与安装解释器不匹配的服务解释器。

回归过程中修复了 C++ schema catalog 未跟踪 schema 文件的增量构建问题。现在新增/删除 schema 会触发 CMake 重新配置，修改 schema 会重新生成 catalog。

## 可复验命令

以下路径是本次本地验证环境的临时路径；其他机器应准备自己的已安装 SDK、目标兼容依赖和 Python 解释器。部署集成测试需要 `openssl`、`mosquitto` 和 pytest。

在 framework 仓库执行：

```bash
URAN_DEPLOY_TEST_SDK=/tmp/uran-deployment-work/sdk \
URAN_DEPLOY_TEST_PYTHON_SITE=/tmp/uran-deployment-work/site \
URAN_PYTHON=/home/feiyu/miniconda3/bin/python3.13 \
bash scripts/test_deployment.sh
ctest --test-dir build/check --output-on-failure
```

在 interfaces 仓库执行：

```bash
PYTHONPATH=bindings/python PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 \
  /home/feiyu/miniconda3/bin/python3.13 -m pytest -q tests
cmake -S . -B build/deployment-check
cmake --build build/deployment-check --parallel 4
ctest --test-dir build/deployment-check --output-on-failure
```

在 plugins 仓库执行：

```bash
PYTHONPATH=/tmp/uran-deployment-work/site PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 \
  /home/feiyu/miniconda3/bin/python3.13 -m pytest -q protocols/mqtt/tests network/frpc/tests
```

测试出现 jsonschema `RefResolver` 和 paho 的 TLS API 弃用提示；均未禁用证书验证，测试通过。旧 Python 兼容依赖与现代 Python 依赖采用环境标记区分。
